BLACKOUT — Technical PRD
Nov 6, 2026 · @Harman Manik
Summary
BLACKOUT is a saved, verifiable emergency exit for DeFi positions. It works when the protocol's website, domain, company or RPC provider fails or is hijacked.
Pitch: "We take down the DeFi app's website, and you can still withdraw directly from its smart contracts."
What the demo proves:
	•	A real withdrawal from the saved kit, with the website and primary RPC switched off by a judge.
	•	A tampered kit is rejected by an independent fingerprint check against an ENSv2 record.
	•	A stolen website key cannot change the release record or swap the name's resolver.
	•	The Exit Guard rejects real attacker calldata from the Curve 2022 and Balancer 2023 frontend hijacks, replayed on mainnet forks.
Protocols covered:
	•	Uniswap v3: live on Sepolia and on a mainnet fork.
	•	Aave v3 and Curve: on a mainnet fork.
Partners targeted: EF (CROPS lead, Anon-RPC tag), ENS (Best Use of ENSv2), Uniswap Foundation.
What it is not: protection against smart-contract exploits, oracle attacks, stolen user keys, or paused or insolvent contracts. The replay lab includes a contract exploit as a control to show this limit honestly.
Problem and threat model
DeFi contracts outlive their websites, but users reach them through those websites. In the frontend incidents below the contracts were fine. Users lost money by signing approvals on a hijacked site.

Correction to the pitch: never claim "no user funds will ever be lost." The honest claim is: if the website dies or is hijacked, you can still exit, and a hijacked site cannot trick the kit into an approval or a foreign recipient.
Users and core flows
Three people use BLACKOUT: the LP or lender who needs to exit, the protocol team that publishes releases, and the security team that runs drills.
Publish (protocol team)
	•	Build the kit reproducibly and compute its sha256.
	•	The release Safe writes org.blackout.release (hash and version) and org.blackout.manifest (exit contracts per chain) on the protocol's ENSv2 name.
	•	Host the kit on the website and on any mirror. Hosting is not trusted; the ENS record is.
Prepare (user, any time before an incident)
	•	Download the kit from the site or any mirror.
	•	Verify it independently: sha256sum blackout-kit.html must match the ENS release record, read with any ENS client or the ENS app.
	•	Take the ENS name from the protocol's docs or the moment you deposit, never from the kit itself.
Exit (user, during an incident)
	•	Serve the kit on http://localhost (npx serve or python3 -m http.server). Wallets don't inject into file:// pages.
	•	Connect the wallet. The kit reads the manifest from ENS through the read quorum.
	•	Adapters find the user's positions from the wallet. No position file is needed.
	•	For each position the kit simulates the exit, runs the Exit Guard, then asks the wallet to sign.
	•	The kit shows "Recovered" only after a confirmed receipt and a positive balance change. It then writes an exit report.
Drill (judge or security team)
	•	Pick the failure: website down, RPC down, or hijacked site.
	•	The harness switches it off for real.
	•	Run the exit. The report records time-to-exit, transaction hashes and balances before and after.
System architecture
The kit sits between ENS and the user's wallet. The company's website and primary RPC are not on the exit path, so switching them off cannot block an exit.

BLACKOUT architecture · release trust, exit kit, chains
Read it top to bottom: the Safe and the website key write different ENS records; the kit reads them through the quorum, runs each exit through the Guard, and only the wallet signs.
Trust boundaries:
	•	Trusted: the wallet and its broadcast RPC, Ethereum, ENS contracts, the release Safe's signers.
	•	Verified, not trusted: the kit file (hash against ENS), RPC answers (quorum), every exit call (Guard).
	•	Not trusted at all: the website, its DNS, its third-party scripts, wherever the kit is hosted.
ENSv2 release and role design
Each protected app gets one ENSv2 name on Sepolia. The website key can write only url; a 2-of-3 Safe owns everything else. A stolen web or DNS key therefore cannot publish a release, swap the resolver or upgrade it.
ENSv2 is deployed on Sepolia (deployments). Mainnet ENSv2 contracts exist, but mainnet resolution still runs through ENSv1 until launch completes, so build on Sepolia.

Setup steps
	•	Register the name with the Sepolia ETHRegistrar into the Safe. Public registration is not confirmed in the docs; if blocked, ask the ENS booth first thing.
	•	Deploy the resolver: VerifiableFactory.deployProxy(PermissionedResolverImpl, salt, initialize([{Safe, ALL_ROLES}], [])) (factory docs). Grant ALL_ROLES only to the Safe; the docs' example grants it to the caller.
	•	The Safe calls setResolver on the registry, pointing the name at the new resolver.
	•	The Safe grants the website key one scoped role for url (resolver docs).
	•	The Safe writes the release and manifest records.
Must-revert checks (run live in the demo)
	•	Website key writes org.blackout.release → reverts with EACUnauthorizedAccountRoles.
	•	Website key calls setResolver on the registry → reverts.
	•	Website key upgrades the resolver proxy → reverts.
	•	Website key grants itself roles → reverts.
	•	The Safe updates the release → succeeds; the kit shows the new version. Versions only go up, so an attacker can't roll back to an old release.
Exit Kit and protocol adapters
The kit is one self-contained HTML file that loads no external code. Three adapters find positions from the wallet and build exit calls that need no approvals.
Packaging
	•	Stack: Vite + Preact (or React) + viem, bundled into one file with vite-plugin-singlefile.
	•	Content Security Policy: default-src 'none'; script-src 'sha256-<build hash>'; style-src 'unsafe-inline'; connect-src https: wss: http://127.0.0.1:*; img-src data:.
	•	Reproducible build: pinned Node and pnpm lockfile, SOURCE_DATE_EPOCH, no timestamps. CI builds twice and the hashes must match.
	•	Serving: http://localhost only. The kit never fetches code after load.
	•	Size target: under 1 MB.

Exit Guard
Every transaction the kit builds passes a pure-TypeScript policy check before the wallet sees it. The Guard rejects anything that is not a known exit to the user's own address, and fails closed on anything it cannot decode.
guard(tx: TxRequest, ctx: { account: Address; chainId: number; manifest: Manifest }): { ok: boolean; reasons: string[] }
Rules, applied in order
	•	Chain: chainId must be listed in the ENS manifest.
	•	Target: to must be on the manifest allowlist for that chain.
	•	Function: the selector must be on the allowlist for that target. Calls nested in multicall are decoded and checked recursively.
	•	Recipient pinned: every decoded recipient argument (collect.recipient, withdraw.to) must equal the connected account. Pools that pay the caller need caller = account.
	•	Always banned: approve, increaseAllowance, EIP-2612 and DAI permit, setApprovalForAll, transfer, transferFrom, and Permit2 permits. The kit never requests typed-data signatures.
	•	No ETH sent: value must be 0.
	•	Simulation: an eth_call at a block pinned across the quorum must succeed and return the expected amounts.
	•	After send: the receipt must show success and each expected token balance must rise. Otherwise the kit reports "Not recovered".
Any decode failure, unknown selector or quorum disagreement means reject. The Guard has no override switch in the UI.
Why this is the protection mechanism to test
In the Curve and Balancer hijacks the attacker's lever was an approval signed on a fake site. Rules 3 and 5 reject that calldata whatever page produced it. Rule 4 rejects a quieter attack that only swaps the recipient. Section "Incident Replay Lab" feeds the attackers' real calldata into this function.
Stretch (P3)
	•	Check a transaction: paste the calldata a live site asks you to sign; the Guard explains whether it is a safe exit.
	•	Hijack detection: hash the live site's main bundle and compare it with org.blackout.site.
Read quorum and network trust
The kit reads from three independent RPC paths. It refuses to sign if fewer than two answer or if they disagree.
	•	Endpoints: endpoints the user enters, plus two public providers, plus Anon-RPC through Nox for Sepolia if it passes its go/no-go. Settings are stored only in the browser.
	•	Agreement: all paths must report the same chain ID. Critical reads (ENS records, ownerOf, positions, balances) are pinned to one block number and compared. Any mismatch stops the flow.
	•	Timeouts: 4 s per call, 2 retries, then the path is marked down.
	•	Broadcast: through the wallet's own RPC. This is a trusted dependency and is disclosed under CROPS "C".
	•	Anon-RPC: Nox is the only listed Sepolia network and is a testnet demo (adopters). Ship its worker inside the kit, pinned by hash, so nothing is fetched at run time. Cap: 2 person-hours, decided by 7 AM Fri. If dropped, the EF entry leads with CROPS.
What each third party learns (CROPS "P"): RPC providers see reads for the user's address. With Anon-RPC they don't see the IP. There is no BLACKOUT server and no analytics.

Incident Replay Lab
For each real frontend hijack, we fork Ethereum mainnet just before a victim's malicious approval, replay the attack, then replay the same moment with BLACKOUT and compare balances. A smart-contract exploit is included only as a control, to show where BLACKOUT does not help.
Tooling
	•	Foundry: forge test with vm.createSelectFork(rpc, block) and vm.transact(txHash), which fetches a historical transaction and executes it on the current fork state (docs). Also vm.rollFork to move a fork to a block or transaction (docs); confirm its transaction-hash overload before relying on it.
	•	Anvil: anvil --fork-url $ARCHIVE_RPC --fork-block-number N so the real TypeScript kit code (adapters and Guard) runs against historical state, using anvil_impersonateAccount.
	•	Archive RPC: a historical fork needs an archive node (Alchemy or Infura archive tier). Cache fork state locally to avoid rate limits.

Finding the replay transactions
The CertiK and Cointelegraph write-ups give dates and mechanisms, but no addresses or hashes in text. Collect them from Etherscan:
	•	Find the drainer or attacker address from incident threads (CertiK Alert, MistTrack, SlowMist) or Etherscan's phishing labels.
	•	On the drainer contract, open incoming token transfers and pick one victim's drain transaction.
	•	From the victim's history, find their earlier approve to the drainer.
	•	Inspect both locally with cast run <hash> and cast tx <hash> input.
	•	Save replay/fixtures/<id>.json with victim, approveTx, drainTx, tokens and block numbers.
Timebox: 2 hours for R1. If Curve 2022 addresses are hard to pin down, use R2 first; Angel Drainer contracts are labelled on Etherscan.
Pipeline (pnpm replay R1)
	•	Fork: createSelectFork at the approve transaction's block, so the state is from before the victim signed.
	•	As it happened: vm.transact(approveTx), then vm.transact(drainTx). Record the victim's balances: the loss.
	•	Counterfactual: a fresh fork at the same block. Skip the approve and vm.transact(drainTx). Expect a revert or zero moved.
	•	Guard: a vitest test loads the real approve calldata from the fixture into guard(). Expect a rejection, with reasons: selector banned, spender not on the allowlist.
	•	Exits at the incident block: Anvil fork at the same block. Impersonate a real 3pool LP and a real Uniswap v3 LP. Run the kit's adapters and Guard, send, and assert positive balance deltas.
	•	Report: a Markdown and HTML table per scenario with lost without BLACKOUT, lost with BLACKOUT, Guard verdicts, exit transactions and gas.
Honesty labels in the report and the demo
Every result is labelled "mainnet fork", "impersonated account" and "counterfactual". Never present a replay as a live mainnet rescue.

Honest limits (say them before judges do)
	•	Does not stop smart-contract exploits; control C1 shows it.
	•	Still trusted: the user's wallet and its broadcast RPC, Ethereum itself, ENS, the release Safe's signers, and sha256sum.
	•	MVP covers Uniswap v3 NFTs held directly, Aave v3 supply-only and Curve 3pool LP. Not Uniswap v4, vaults or staked positions.
	•	The user must save or fetch the kit and know the ENS name from a source other than the kit.
Q&A prep
	•	"Why not Etherscan?" Blockscout's own guide shows the manual route (guide). It needs the contract address, ABI fields, raw amounts and a separate collect step. An explorer is also another company frontend. BLACKOUT is one click, pins the recipient and cannot send an approval.
	•	"Why would anyone save it before an outage?" Offer it at deposit time. Protocols host it on every mirror, and wallets could cache kits by ENS hash. The hash in ENS, not the host, makes any copy safe.
	•	"Who holds the release key?" The protocol's own Safe, separate from web operations. A stolen website or DNS key cannot publish.
	•	"Why ENS and not a hash in the README?" A README lives on the same infrastructure that gets hijacked. ENS gives an updatable record with enforced role separation that any client can read.
	•	"Uniswap v4?" v4 positions aren't enumerable the same way. Discovery would use a log scan over the same read quorum; it is next on the roadmap.
	•	"Privacy?" No server, no analytics. RPC providers see reads; Anon-RPC hides the IP when enabled.
