# BLACKOUT Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship BLACKOUT end to end: a verifiable single-file exit kit, driven by ENSv2 records on Sepolia, that withdraws Uniswap v3 / Aave v3 / Curve 3pool positions through a fail-closed Exit Guard and a 3-path read quorum. Also ship a Fire Drill harness, an Incident Replay Lab, and the submission docs.

**Architecture:** A pnpm TypeScript monorepo of small pure packages: `core`, `guard`, `quorum`, `ens`, `adapters`, `exec`. A Vite + Preact app bundles them into one HTML file with a strict CSP. Foundry handles the ENSv2 setup scripts, the permission tests and the mainnet-fork replays. A docker-compose harness breaks the site, the RPC and the DNS for real.

**Tech Stack:** Node 22, pnpm 9, TypeScript 5, viem 2, vitest, fast-check, Preact, Vite + vite-plugin-singlefile, Playwright, Foundry (forge/anvil/cast), Docker Compose, nginx, GitHub Actions.

**Spec:** `docs/spec/BLACKOUT-technical-PRD.txt`. Also carry the review deltas below, which are decisions layered on the spec.

## Decisions layered on the spec (from the pre-build review)

1. **"Check a transaction" is P0**, not P3. It is how the demo's "hijacked site asks for approve → Guard explains the block" beat really works: paste the hijack's calldata into the kit's checker.
2. **Kit integrity is verified outside the kit.** `scripts/verify-kit.sh` (cast + sha256sum) is the main verifier. The kit only *displays* the ENS release hash, with instructions; it never claims to verify itself.
3. **Version rollback:** the kit stores the highest release version seen (try/catch localStorage) and warns on a decrease. The docs no longer claim "versions only go up" is enforced on chain.
4. **Uniswap exit variants:** `liquidity == 0 && owed > 0` → `collect`-only. Expected deltas list only tokens with an expected amount > 0. WETH stays as WETH (no unwrap: it would break recipient pinning).
5. **CSP `connect-src`** includes both `http://127.0.0.1:*` and `http://localhost:*`.
6. **Two quorums:** the ENS quorum (Sepolia) and the target-chain quorum (Sepolia, an Anvil fork, …) are separate objects.
7. **Bootstrap constants** (UniversalResolverV2 address, ENS chain ID) live in `config/networks.json`, are hashed into the kit, and are documented as the trust root.
8. **R2 may be permit-based** (off-chain typed data). The fixture schema allows `approveTx` *or* `permitTypedData`.

## Global Constraints

- Node `22.x` pinned in `.nvmrc` and `engines`. pnpm `9.x` via `packageManager`. A committed lockfile.
- Kit CSP, verbatim apart from decision 5: `default-src 'none'; script-src 'sha256-<build hash>'; style-src 'unsafe-inline'; connect-src https: wss: http://127.0.0.1:* http://localhost:*; img-src data:`
- The kit loads zero external code; it never fetches code after load. Size < 1 MB.
- Reproducible build: `SOURCE_DATE_EPOCH`, no timestamps. CI builds twice and the sha256 values must match.
- Served only from `http://localhost` (`npx serve` / `python3 -m http.server`).
- ENS text keys: `url`, `org.blackout.release`, `org.blackout.manifest`, `org.blackout.site`.
- Release record format: `sha256:<64 lowercase hex>;v=<positive integer>`.
- Default slippage 0.5% (50 bps). Min amounts = simulated output × (1 − slippage), from an `eth_call` at the pinned block.
- Quorum: 3 paths, ≥2 must answer, all answering must agree, same chain ID. 4 s timeout per call, 2 retries, then the path is marked down.
- "Recovered" only when receipt `status == 1` **and** every expected token's balance rose. Otherwise "Not recovered" plus the reason.
- Guard: no UI override. Decode failure, unknown selector or quorum disagreement → reject.
- Broadcast goes via the wallet's RPC only. The kit never requests typed-data signatures.
- No analytics or trackers anywhere (kit, hosted page).
- Replay outputs are always labelled `mainnet fork`, `impersonated account`, `counterfactual`.
- Protocol addresses come only from the ENS manifest, never from adapter code.
- License MIT. **Commit after every task and push to `origin main` (small, frequent pushes).** Commit trailer: `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Uniswap position with `liquidity == 0` but `tokensOwed > 0`.** Expect a `collect`-only exit, not a revert. Test lives in Task 5.1.
2. **Out-of-range position, one token amount 0.** Expect "Recovered" when the single expected token rises. Tests in Tasks 5.1 and 6.1.
3. **RPC paths at different heights.** Expect the pinned block = min(latest) across answering paths, reads at that block, no false disagreement. Test in Task 3.1.
4. **Wallet on the wrong chain.** Expect the kit to ask for a switch and refuse to build or send. Test in Task 7.3.
5. **Manifest missing, malformed JSON, or chain not listed.** Expect fail-closed with a plain-language message, never a crash. Tests in Tasks 1.2 and 7.3.

### Task 2.2: Guard rules and explanations

**Files:** Create `packages/guard/src/{guard.ts,explain.ts,index.ts}`. Test: `packages/guard/test/guard.test.ts`.

**Interfaces:**
```ts
interface GuardCtx { account: Address; chainId: number; manifest: Manifest }
interface GuardResult { ok: boolean; reasons: GuardReason[] }
type GuardReason = { code: 'CHAIN'|'TARGET'|'SELECTOR'|'BANNED'|'RECIPIENT'|'CALLER'|'VALUE'|'DECODE'; detail: string }
guard(tx: TxRequest, ctx: GuardCtx): GuardResult
explain(r: GuardResult): string[]          // plain-language sentences, e.g. "This asks you to approve 0xab…cd to spend your tokens. Exits never need approvals."
```
Rule order follows the spec, and reasons accumulate:
1. CHAIN
2. TARGET (to ∈ manifest entries for chain with non-empty selectors)
3. SELECTOR (outer and every nested selector ∈ that target's list)
4. RECIPIENT (every decoded recipient == account, case-insensitive)
5. CALLER (`paysCaller` ⇒ `tx.from == account`)
6. BANNED (any outer or nested selector ∈ BANNED_SELECTORS)
7. VALUE (value must be 0n)

Decode failure → a single DECODE reason, ok=false. Also reject when `tx.chainId !== ctx.chainId`.

### Task 3.1: Quorum client

**Files:** Create `packages/quorum/src/{quorum.ts,errors.ts,index.ts}`. Test: `packages/quorum/test/quorum.test.ts` (fake RPC servers via `node:http`).

**Interfaces:**
```ts
interface QuorumOpts { urls: string[]; minAnswers?: 2; timeoutMs?: 4000; retries?: 2; fetchFn?: typeof fetch }
interface Quorum {
  status(): { url: string; up: boolean; lastError?: string }[]
  chainId(): Promise<number>                          // all answering must agree
  pinBlock(): Promise<bigint>                         // min(latest) across answering paths
  call(req: { to: Address; data: Hex; from?: Address }, block: bigint): Promise<Hex>
  read<T>(args: ReadContractParams, block: bigint): Promise<T>  // viem encode/decode around call()
  getBalance(addr: Address, block: bigint): Promise<bigint>
  getReceipt(hash: Hex): Promise<TransactionReceipt | null>     // agreement on status + blockHash
}
createQuorum(opts: QuorumOpts): Quorum
class QuorumError extends Error { kind: 'TOO_FEW'|'DISAGREE'|'CHAIN_MISMATCH' }
```
Raw JSON-RPC over `fetch` with `AbortController` (no viem transport, so the timeout and retry semantics are exact). Each path gets 1 + 2 retries, then is marked down. Fewer than 2 answers → TOO_FEW. Any two differing answers → DISAGREE.

  - Two down → TOO_FEW.
  - One lying on `eth_call` → DISAGREE.
  - One with a different chainId → CHAIN_MISMATCH.
  - Heights 100/101/103 → `pinBlock() === 100n` and every `eth_call` was sent with block `0x64` (Review Focus 3).
  - A slow server (5 s) is treated as down after 3 attempts.
